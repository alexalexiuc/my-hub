---

## Summary

The Calorie Tracker MCP server lets an AI client log meals, retrieve nutritional
summaries, manage the user's dietary profile, and track body measurements over time
on behalf of the authenticated user. Implemented as a Fastify module backed by
PostgreSQL on the self-hosted platform.

The day card's "Add meal" button opens that modal; there is no separate inline quick-add form. The meal type is choosable only when adding, since editing is addressed by the `(dayOfWeek, mealType)` slot.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| FR-23 | Because creating a menu for a week that already has one replaces it (FR-15), the Hub must not let that happen unannounced: the header button reads "Create" only while no menu exists and "Plan another week" afterwards, and the create modal warns — and relabels its submit to "Replace menu" — whenever the selected week already holds a menu, naming the shopping list and logged meals as collateral.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| FR-24 | A day that has already passed is read-only as a plan: its "Add meal", "Edit this meal" and "Remove this meal" controls are all disabled (not hidden), matching the create modal's disabled past-day tabs, each explained by a tooltip on a wrapper element (a disabled button shows none of its own). The menu is the plan, so rewriting it after the fact would let adherence — logged/planned per day — be scored against a plan written to match; deleting an unfollowed meal would likewise drop the day out of the denominator. **"Log" stays enabled on past days** — recording a meal that was eaten, late, is the one change that makes the record more accurate. Today is not past and stays fully editable.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| FR-25 | `calories_plan_week` plans for variety by default. Repetition is opt-in: the assistant repeats a dish only where past menus show it is a staple, or where batch cooking genuinely saves work (one batch eaten across 2-3 days, stated in `prepNotes`) — never the same breakfast, lunch or dinner on all seven days. The rule is stated for the no-history case explicitly, since a first menu has no signal to read and would otherwise default to repeating. A user who wants the same dish daily asks for it; a user who wants variety should not have to.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| FR-26 | The profile stores an optional **training time band** (`morning` \| `midday` \| `evening`) alongside gym days — a band, not a clock time, because what changes a plan is only which meals fall either side of the session. It is set from the Hub profile form and `calories_update_profile`, and read from `calories://profile`, `calories_plan_week` and `calories_get_weekly_menu`. `calories_plan_week` uses it to shape gym days: lighter carb-led meal before training, largest and most protein-heavy after, `pre_workout` / `post_workout` slots placed accordingly. When gym days are set but the band is not, the assistant asks rather than guessing. One band per user, not per day — per-day timing is deliberately deferred until there is evidence it varies.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| FR-27 | Logging a planned meal is reversible. The same control that logs a slot un-logs it, and "Log full day" becomes "✓ Full day logged", which undoes the whole day — logging a day costs one tap, so undoing it must too. Undo removes both the slot marker and the journal entry the log created (`unlogMenuMeal`, one transaction), matching the entry on the fields `logMenuMeal` wrote; if the user has since edited that entry by hand, only the marker is removed. Undo stays available on past days, where editing and deleting the meal are disabled (FR-24) — without it a mis-tap there would be permanent.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| FR-28 | A menu's title and prep notes are editable in the Hub (`PATCH /api/calories/menu/[menuId]/details`), not only through `calories_plan_week` / `calories_set_prep_notes`. The title renders beside the week range as a heading — not in the section-label style, which reads as UI chrome — and only when set. Empty input clears the field rather than storing `""`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| FR-29 | The create-menu modal can start from the menu on screen ("Copy meals from …"). It carries the meals **and** the title, prep notes and shopping list, since all three describe those same meals; the copy is disclosed in the modal ("Also copied: …") rather than applied silently. Meals land as editable rows, never as a direct duplicate, and days already past are skipped. A failed shopping-list fetch degrades to copying without it. This is transport, not authoring — FR-18 still governs who writes the list's content.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| FR-30 | On phones the menu shows a row of seven day chips above the stacked cards, each jumping to that day; the row shares the width equally so all seven are reachable without scrolling, and today is highlighted. Hidden from `md` up, where the grid already shows the whole week.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| FR-31 | The order meals are displayed in follows the training time band (FR-26), not a fixed list. The band names the meal that follows the session — `morning` → breakfast, `midday` → lunch, `evening` → dinner — and the `pre_workout` / `post_workout` pair is placed immediately before that meal; `snack` and `other` stay at the tail, having no fixed moment in the day. With no band set the pair sits at the tail instead, since there is no session to anchor it to and a default would reorder the plan on a guess. One shared rule (`mealOrder(gymTime)`) drives every place meal slots are listed — the day card's rows, the "add a meal" slot list, the log-a-meal modal's type chips, and which meal the Today page calls next — otherwise a morning trainer's pre-workout meal renders after dinner. Display only: no per-meal time is stored. The log-a-meal modal has no other reason to load the profile, so it reads the band through `useGymTime()` and falls back to the unset order while the request is in flight or if it fails.                                                                                                                                                                                                                                                               |
| FR-32 | The log-a-meal modal's meal-type chips are laid out as a fixed-column grid — three columns below 360px, four above — with every chip at least 44px tall and its label kept on one line. Seven labels never share a row: at 320px they overflowed the container by 26px and clipped the last type, and a wrapping flex row stretches the last row's items to fill the width so the rows do not align. Seven columns are wrong even on desktop, where the modal is capped at 480px and each column would come out narrower than on a phone.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| FR-33 | Editing a logged meal can clear a field, not only change it. The form sends an emptied calorie count, macro or note as explicit `null`, the update endpoint accepts null alongside the value, and the service distinguishes `undefined` (leave alone) from `null` (clear). Previously every path collapsed an empty field to `undefined`, so a saved calorie count could never be removed and the save reported success while changing nothing. Meal numbers are validated as non-negative on both the form and the API, and dates must be YYYY-MM-DD.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| FR-34 | The gym-day bonus (FR-16) applies wherever a day's target is shown, not only in the weekly menu: the Today donut, its range line and the Progress week chart all resolve the target per day via `dayTargetKcal`, and Today labels a training day explicitly. A single flat target marked every gym day as over on one tab while the menu called the same day on track. The Progress chart draws one reference line per distinct target in the week, so a mixed week shows both the base and the gym-day level.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| FR-35 | The Hub profile form owns weight. It is stored as a `weight` measurement rather than a profile column, but it is entered and shown with the rest of the profile, because every calorie target depends on it: without a weigh-in the feature reports "no goal set", and its own "Set up profile" link led to a form that could not fix that. Saving writes a new measurement only when the value actually changed, so re-saving the form does not stamp duplicates into the weight history.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| FR-36 | Body measurements can be edited, not only added and deleted (`PATCH /api/calories/measurements/[id]`), and both controls are reachable by touch — they are visible by default and only hover-gated from `md` up. Revealing them on hover alone made them unusable on a phone, where measurements could be created but never corrected. Dates render as "Today"/"Yesterday"/short date rather than raw ISO.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| FR-37 | The Hub exposes a Calendar tab under Calories (`/calories/calendar`): a month grid, one 7-column layout unchanged between mobile and desktop (cells just get narrower on a phone, no separate stacked view), navigated month-to-month. Each in-month day cell shows its total kcal tinted by the same red/amber/green adherence rule `intakeBarColor` already applies on Progress — a day reads the same colour on both tabs. Clicking a day opens a read-only detail modal with that day's kcal-vs-target bar, protein/carbs/fat totals, its logged meals, and — when the week it falls in has a weekly menu — that day's planned meals with their logged/unlogged state. Both meal lists are ordered by the training-time band per FR-31, not a fixed list.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| FR-38 | Logging a meal outside the "Log it" control — via `calories_log_meal` (the assistant) or the Hub's "add a meal" form — still fulfills its planned slot, so the Today page's "Next planned meal" card and the weekly menu's logged state stay accurate regardless of which path was used to log. `logMeal` calls `tryLinkLoggedMealToPlan(userId, date, mealType, mealLogId)` after journaling: if that date's week has a menu with a not-yet-logged planned slot for the same meal type, the slot's day-log marker is written pointing at the journal row just created — the same state `logMenuMeal` produces via the "Log it" button. The menu organizes what to eat, it doesn't police it: fulfillment does not require the logged meal to match the planned dish — a variation ("no breading" on a planned breaded dish, an added side) or an outright substitution both fulfill the slot the same as an exact match, and the planned menu item itself is never rewritten to match what was actually eaten, so "planned X" stays visible next to "logged Y" in the journal. An already-logged slot is left alone (`onConflictDoNothing`) rather than double-fulfilled or re-linked. Best-effort — a failure here is logged and does not fail the meal log itself, since the journal write already succeeded. |

## Technical Requirements

| ID    | Requirement                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TR-01 | Implementation lives in `packages/mcp-server/src/calories/` — `server.ts` wires tools; `tools/` contains `profile.ts`, `meals.ts`, `summary.ts`, and `measurements.ts`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
| TR-02 | DB schema uses three tables: `calorie_profiles` (age, sex, activity, goal), `meal_logs`, and `body_measurements` (time-series per user+type). Measurement type metadata (key/label/unit) is defined in shared constants.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| TR-03 | Access is protected by OAuth 2.1 PKCE; `mcpAuthHandler` validates the Bearer token and attaches `userId` to the request.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| TR-04 | All DB queries go through `packages/shared/src/services/calories/` and `packages/shared/src/services/measurements/` — no raw Drizzle in `mcp-server`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| TR-05 | MCP transport uses `WebStandardStreamableHTTPServerTransport` in stateless mode (new server instance per POST).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| TR-06 | Measurement types are defined in `packages/shared/src/constants/measurements.ts` as a constant list of `{ key, label, unit }` objects (e.g. `weight`/kg, `height`/cm, `body_fat`/%), consumed by Hub and MCP services.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| TR-07 | `calories_get_profile` and TDEE-dependent summary tools must call `getLatestMeasurementsPerType(userId)` and pass the latest `height`/`weight` values to `calculateTDEE`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| TR-08 | Date defaults for calorie daily/history flows must use the authenticated user's stored timezone when available (falling back to server-local behavior only when timezone is unset/invalid).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| TR-09 | Weekly-menu storage uses four tables: `weekly_menus` (user + week_start), `weekly_menu_meals` (unique slot constraint `uq_weekly_menu_meal_slot`), `weekly_menu_day_logs` (logged-slot markers, unique per slot), and `weekly_menu_shopping_items` (unique per menu + text). Child tables cascade on menu delete. `weekly_menu_meals` also carries `week_start` (copied verbatim from the parent menu at insert time — a menu's week never changes after creation) and a generated `date` column (`GENERATED ALWAYS AS (week_start::date + day_of_week days) STORED`, indexed) so date-scoped reads don't need to resolve date → weekStart → menu → dayOfWeek by hand; every write path sets `week_start` via `getMenuWeekStart`, and every read/return path selects the explicit `weeklyMenuMealColumns` list (excluding `week_start`) so the internal column never leaks into `WeeklyMenu` API/MCP responses. |
| TR-10 | All weekly-menu queries live in `packages/shared/src/services/calories/weekly-menu.ts` and `shopping-list.ts`. Menu ownership checks go through `hasAccessToMenu` (1s promise cache); every code path that deletes a menu (delete, replace-on-create, delete-all) must evict the cache entry to avoid FK violations from stale grants.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| TR-11 | Hub route contracts for the feature are Zod schemas in `packages/hub/src/app/api/calories/menu/menu.schemas.ts`, shared by the routes (`route({ body, response })`) and the client (`apiFetch` `bodySchema`/`responseSchema`). The duplicate-slot rule is `hasDuplicateMealSlot` from `@my-hub/shared/utils`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| TR-12 | Meal ingredients are a nullable `text[]` column on `weekly_menu_meals` — deliberately unstructured (quantities live inside each string), not a normalised recipe model. Every write path normalises through one helper in `weekly-menu.ts`: trim, drop blanks, drop case-insensitive duplicates, and collapse an empty result to `null` so "no ingredients" has a single representation.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| TR-13 | `rowToProfile` in `packages/mcp-server/src/calories/models/profile.ts` is the single read surface for the calorie profile — it feeds the `calories://profile` resource and the `calories_update_profile` response. Every profile column must reach it except internal keys (`id`, `userId`), `createdAt`, and `automationApiKey` (a secret). A unit test asserts exactly that against a fully-populated row, so a column added to the schema cannot silently fail to reach the assistant — which had already happened to `gymDayCalorieBonus` and the three macro targets.                                                                                                                                                                                                                                                                                                                                      |
| TR-14 | `getDailySummariesForRange(userId, start, end)` in `packages/shared/src/services/calories/day-summaries.ts` returns zero-filled per-day `{date, kcal, protein, carbs, fat, mealCount}` for an arbitrary date range, built on `getMealsForDateRange`. `GET /api/calories/calendar?month=YYYY-MM` (`packages/hub/src/app/api/calories/calendar/route.ts`, schemas in the sibling `calendar.schemas.ts`) layers `dayCalorieTargets` on top per day to add `target`/`min`/`isGymDay`, so a day's ceiling matches Progress and the weekly menu rather than being re-derived a third way.                                                                                                                                                                                                                                                                                                                             |

## Acceptance Criteria

- [x] All calorie-tracker MCP tools are registered: `calories_log_meal`, `calories_get_meals`, `calories_delete_meal`, `calories_get_daily_summary`, `calories_get_weekly_summary`, `calories_get_remaining`, `calories_get_profile`, `calories_update_profile`, `calories_log_measurement`, `calories_get_measurements`, `calories_get_measurement_types`, `calories_delete_measurement`.
- [x] A Claude client authenticated with a valid OAuth token can log a meal, retrieve the daily summary, and delete the meal.
- [x] A Claude client can log a body measurement by type key, retrieve measurements filtered by type/date, and delete a measurement.
- [x] `calories_get_profile` returns `latest_measurements` alongside the profile and calculated TDEE.
- [x] TDEE returns `null` when no height or weight measurement exists for the user.
- [x] An unauthenticated request returns 401.
- [x] All weekly-menu MCP tools are registered: `calories_plan_week`, `calories_get_weekly_menu`, `calories_set_menu_meal`, `calories_remove_menu_meal`, `calories_delete_weekly_menu`, `calories_set_prep_notes`, `calories_set_shopping_list`.
- [x] `calories_plan_week` saves meals, prep notes, and the shopping list in a single call; `calories_set_menu_meal` adds a meal to an empty slot and replaces the dish in a filled one.
- [x] Creating a menu with a duplicate (dayOfWeek, mealType) slot is rejected with a clear error on both the Hub API and the MCP tool.
- [x] `calories_plan_week` calorie warnings account for the gym-day bonus, and `calories_update_profile` can set both `gymDays` and `gymDayCalorieBonus`.
- [x] Logging a planned meal writes the journal entry and the day-log marker atomically; retrying a logged slot does not duplicate the journal entry.
- [x] A meal can carry an optional ingredient list end to end: set via `calories_plan_week` / `calories_set_menu_meal` or the Hub create/meal-detail modals, normalised on write, and shown collapsed on the meal row.
- [x] Add and edit go through one meal-detail modal — the day card has no separate inline add form, and both paths write meal type, description, calories, macros and ingredients.
- [x] Once a menu exists the header button reads "Plan another week", and picking a week that already has a menu warns that creating replaces it (submit relabelled "Replace menu").
- [x] The training time band round-trips: set in the Hub profile form, persisted to `calorie_profiles.gym_time`, shown on the profile card, and readable by the assistant from the profile resource and both weekly-menu tools.
- [x] A logged meal can be un-logged, individually and for a whole day, on past days too — the journal entry goes with the marker (Playwright journey covers log → undo → re-log).
- [x] Title and prep notes can be set from the Hub and appear without a reload.
